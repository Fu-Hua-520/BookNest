# BookNest 并发安全 / 并发性能 / 查询性能优化方案

> 只给方案，不含改动。所有问题点均已核对到文件与行号，行号基于 2026-09-14 的代码快照。

## 总览：分四层，按投入产出比排序

| 层 | 主题 | 典型收益 | 风险 | 建议顺序 |
| --- | --- | --- | --- | --- |
| 第一层 | 正确性修复 | 消除丢更新 / 假报错 | 极低 | 先做 |
| 第二层 | 查询与索引 | 列表接口查询次数降一个数量级 | 低 | 紧接着做 |
| 第三层 | Redis 缓存与计数器 | 热点请求不再进 DB | 中（一致性） | 数据量起来后 |
| 第四层 | MQ 与可扩展性 | 支撑多实例、削峰 | 中高（架构） | 有扩容需求时 |

**论坛实际负载特征**（决定优化重点）：
- 读远多于写，且读极度集中在**首页列表、帖子详情、热门书吧**三处，天然适合缓存。
- 写集中在**点赞、评论、浏览量**，都是「高频但轻量、且允许最终一致」的计数类操作，天然适合 Redis 缓冲 + 异步落库。
- 真正的强一致要求只落在**发帖、删帖、审核**这类低频操作上，不必为它们做复杂设计。

## 第一层：正确性修复（零成本，必须先做）

这一层不提升吞吐，但当前的并发缺陷会**静默产生错误数据**，越晚修越难回溯。

### 1.1 吧内经验值改原子自增（最高优先级）

**现状**：`BarServiceImpl.addExp`（L259-289）走「先 `selectByBarAndUser` 读 → 内存里 `exp += granted` → `updateExp` 全量覆盖」。

```java
263→  BarMember member = barMemberMapper.selectByBarAndUser(barId, userId);  // 读
281→  exp += granted;          // 内存加
288→  persistExp(member, exp, dailyExp, today);  // 整行覆盖写回
```

`BarMemberMapper.xml` L30-38 的 `updateExp` 是 `set exp = #{exp}`（全量赋值），不是 `exp = exp + n`。

**后果**：
- 同一用户在不同帖子并发点赞 / 评论，两线程读到相同旧值，后写覆盖先写 → **经验值丢失**。
- `daily_exp` 的每日 100 上限校验基于读到的旧值 → **上限被绕过**，等级会虚高。
- 三处高频入口都调它：发帖、评论、点赞（含取消时的 -2）。

**方案**：
1. `updateExp` 改为 `set exp = exp + #{delta}, level = ..., daily_exp = daily_exp + #{delta}`，把「加多少」交给 SQL 算。
2. 但 `level` 依赖 `exp` 的最终值 —— 改为 `level = #{level} where exp = #{expectedExp}`（乐观锁 CAS），或干脆由 `updateExp` 内部用 `case when exp+? >= 阈值 then ... end` 推导，避免读改写。
3. `daily_exp` 的当日额度需要「先判断再加」，改成条件更新：`... set daily_exp = daily_exp + ? where bar_id=? and user_id=? and (daily_date <> ? or daily_exp + ? <= 100)`，用**受影响行数**判断是否生效。这样并发下也不会突破上限。
4. 若嫌 SQL 复杂，退一步用 `select ... for update` 把这一行锁住（`uk_bar_user` 唯一键保证行级锁精准），代价是这个用户在本吧的经验累加串行化 —— 可接受，因为它本身低频。

### 1.2 点赞 / 收藏 / 关注 / 入吧：TOCTOU 竞态 + 唯一键异常未兜底

**现状**：四处都是「先 select 判断 → 再 insert/delete」：

| 位置 | 行号 | 唯一索引兜底 |
| --- | --- | --- |
| `PostInteractionServiceImpl.togglePostLike` | L313-340 | `post_like.uk_post_user` |
| `PostInteractionServiceImpl.toggleCommentLike` | L274-298 | `post_comment_like.uk_comment_user` |
| `PostInteractionServiceImpl.togglePostCollect` | L368-394 | `post_collect.uk_post_user` |
| `FollowServiceImpl.follow` | L34-50 | `user_follow.uk_follower_followee` |
| `BarServiceImpl.follow` | L104-112 | `bar_member.uk_bar_user` |

**后果**（两条不同的错误方向，都是真实可见的）：
- **并发点赞**：两线程都查不到 → 都 insert → 第二条撞唯一键抛 `DuplicateKeyException`。这些方法**都没有 try/catch**，异常冒泡到 `GlobalExceptionHandler` → 用户看到报错，而不是幂等地「已点赞」。
- **并发取消点赞**：两线程都查到记录 → 都 delete 成功（delete 不报错）→ 都执行 `decrementLikeCount` → **计数被减两次**，可能出现负数或明显偏低。
- 关注同理，还会导致**通知重复投递到 MQ**。

**方案**：
1. **insert 侧**：捕获 `DuplicateKeyException`，视为「已存在」直接返回成功（幂等语义）。唯一索引就是并发正确性的最终裁判，不要靠 select 判断。
2. **delete 侧**：用 `deleteByPostAndUser` 的**受影响行数**决定是否扣减 —— 只有真的删掉了（返回 1）才 `decrementLikeCount`。目前是「删完就扣」，没有看行数。这是并发重复扣减的直接原因。
3. **计数一致性**：给 `like_count` 加 `unsigned` 或 `greatest(like_count - 1, 0)` 兜底，避免负数污染展示。
4. 更彻底的做法是把「是否已点赞」下沉到唯一索引 + `insert ignore` / `delete` 的返回值上，Java 侧完全不判断存在性。

### 1.3 慢活移出事务

**现状**：

| 位置 | 行号 | 事务内做了什么 |
| --- | --- | --- |
| `PostServiceImpl.publishPost` | L86-100 | 事务内 `uploadContent()` **上传 OSS** |
| `PostServiceImpl.updatePost` | L300-333 | 事务内上传新正文 + 删除旧正文 |
| `PostServiceImpl.deletePost` | L345-359 | 事务内 `aliOssUtil.delete()` |
| `PostInteractionServiceImpl.publishComment` | L70-121 | 事务内发 MQ + `addExp` |
| `PostInteractionServiceImpl.togglePostLike` | L313-350 | 事务内发 MQ + `addExp` |

**后果**：
- OSS 是外部网络 IO，耗时几十到几百毫秒且会抖动。**被拖住的是数据库连接**，高并发下发帖会迅速耗尽 Druid 连接池，把整个服务拖死 —— 这是本项目最可能的雪崩点。
- 事务未提交就发 MQ，消费端可能先于数据可见时间落库（通知指向一个「还不存在」的帖子）；配合 1.3.4 的消费重试会放大。
- `addExp` 失败会回滚整条评论 —— 评论与经验耦合在一个事务里，粒度偏大。

**方案**：
1. **上传前置**：`publishPost` 先在事务外把正文传到 OSS，拿到 objectName，再开一个只含 DB 写入的短事务。
2. **删除后置**：`deletePost` / `updatePost` 先提交 DB，再删 OSS 旧对象；失败只记日志（孤儿对象可后续清理，比拖住事务划算）。或用 `afterCommit` 注册回调。
3. **MQ 后置**：统一用 `TransactionSynchronizationManager.registerSynchronization(afterCommit)` 投递通知。项目里 AI 机器人触发（`triggerAiBotsAfterCommit`）已经这么做了，通知应当照同一模式改造 —— 现成的模式，直接复用。
4. **经验解耦**：`addExp` 改 `REQUIRES_NEW` 或直接异步化；点赞的经验加减不应该让点赞失败。

### 1.4 MQ 消费幂等

**现状**：`NotificationConsumer.onNotification`（L27-28）是**非幂等的 `insert`**；`application.yml` L44-51 配了 `max-attempts: 3` 重试。生产端 `convertAndSend` 无 publisher confirm。

**后果**：
- 消费抛异常重试 → 同一条通知 **insert 三次**，用户看到 3 条重复通知。
- 生产端投递失败**静默丢失**，通知不落库且无告警。

**方案**：
1. `notification` 表加业务幂等键（如 `receiver_id + source_id + anchor_id + type` 的唯一索引），消费端 `insert ignore` 或捕获唯一键异常。
2. 或者用 Redis `setIfAbsent("notify:dedup:{msgId}")` 做消费去重，TTL 覆盖重试窗口。
3. 生产端开 publisher confirm + return 回调，失败落本地重试表或直接落库降级（通知丢了比整个操作失败好）。

### 1.5 其他细节

- `BooklistServiceImpl` L259-264：`sortOrder = items.size() + 1` 是读改写，并发加条目会产生**重复序号**。改为 `select max(sort_order) + 1` 或直接用自增。
- `TagServiceImpl.updateTag` L161-167：`useCount` 读改写。该列已降级为展示用不到，建议直接**停止写入**该列，全站只认 `post_tag` 实时统计。
- `post_comment` 的删评论递归扣数：`decrementCommentCountBy` 已是原子操作，但要确认递归删除与计数在同一事务内。

## 第二层：查询与索引（收益最大，成本最低）

### 2.1 消灭 N+1：这是当前最大的性能黑洞

**问题清单**（全部是「循环体内发起查询」）：

| 位置 | 行号 | 每页查询次数 |
| --- | --- | --- |
| `PostServiceImpl.toPostVO` | L378-420 | 每条帖子 3 次（分类/书/作者）+ 标签逐条查（**双层循环**） |
| 调用点 `listPosts` | L226-233 | 10 条 → **≥40 次** |
| 调用点 `listMyCollectedPosts` | L257-280 | 同上 |
| 调用点 `searchPosts` | L290-293 | 同上 |
| `PostInteractionServiceImpl.buildCommentVO` | L453-500 | 每条评论最多 5 次（机器人/用户/父评论/点赞态） |
| 调用点 `listComments` | L185-190 | 10 条评论 → **≥40 次**，且评论**无分页全量返回** |
| `ChatServiceImpl.getConversations` | L46-51 | 每会话 2 次（用户信息 + 未读数），N 个会话 → **1+2N** |
| `ChatGroupServiceImpl.buildGroupVO` | L430-449 | 每群 3~4 次（owner / memberCount / unreadCount / pendingJoin） |
| `CategoryServiceImpl.toBarVO` | L506-510 | 每吧 1 次查吧主，且基础数据来自**全表** `listAll` |
| `FollowServiceImpl.listFollowing/listFollowers` | L75-98 | 每条关注 1 次查用户，且**无分页** |
| `ChatGroupServiceImpl.createGroup` | L71-72 | 循环内逐条校验用户存在 |

**方案（统一套路，一次性收口）**：
1. **帖子列表**：先拿到本页 postIds，然后批量一次性查出
   - 分类：`categoryMapper.selectByIds(distinct categoryIds)` → `Map<id, Category>`
   - 书籍：`bookMapper.selectByIds(...)` → `Map<id, Book>`
   - 作者：`userMapper.getUserByIds(...)` → `Map<id, User>`
   - 标签：`postTagMapper.listTagIdsByPostIds(postIds)` 一次拿全部关联，再 `tagMapper.selectByIds(allTagIds)` 一次拿全部标签，在内存里分组
   然后把 `toPostVO(post)` 改成 `toPostVO(post, categoryMap, bookMap, userMap, tagsByPost)` —— **纯内存组装，零查询**。10 条帖子从 40+ 次降到 4 次。
2. **评论列表**：同套路批量查机器人/用户/父评论，点赞态用**一条** `selectByCommentIdsAndUser(commentIds, currentId)` 返回 `Set<commentId>`。并且**评论必须补分页**（当前是全量），否则热门帖（几百层楼）每次进详情页都要全量拉取。
3. **聊天会话**：`findUserConversations` 的 SQL 里直接 `join user` 把对端昵称/头像带出来；未读数用一条 `group by conversation_id` 的聚合查出来，或从 Redis 未读计数读（见第三层）。**1+2N → 2**。
4. **书吧列表**：`listAll()` 全表改为「只查可见吧」；吧主信息批量查；`loadPostCounts` 的一次 GROUP BY 保留（这个已经是合并写法，是好的）。

### 2.2 补齐组合索引

当前缺的关键索引：

| 表 | 建议索引 | 解决的查询 |
| --- | --- | --- |
| `chat_message` | `(receiver_id, is_read)` | `countUnread`（**当前全表扫**） |
| `chat_message` | `(conversation_id, create_time)` | `findMessages` 的 `order by create_time`（当前只有单列 `idx_conversation`，排序要 filesort，深翻页更糟） |
| `post` | `(audit_status, status, publish_time)` | 首页列表最常见的过滤 + 排序组合 |
| `post` | `(category_id, audit_status, status, publish_time)` | 书吧内帖子列表 |
| `post_collect` | `(user_id, create_time)` | 收藏列表按时间倒序 |

**关于 `hot` 排序**：`PostMapper.xml` L55-57 的 `order by (view_count + like_count*5 + comment_count*3) desc` 是**表达式排序，任何索引都走不了，必然 filesort**。低频场景可接受；如果要让「热榜」真正可扩展，方案是：
- 用 Redis ZSet 维护热榜（score = 热度分），只读 Top N；或
- 用定时任务（当前**项目里没有任何 `@Scheduled`**）每 5 分钟把热度分物化到 `post.hot_score` 冗余列，排序走 `(audit_status, status, hot_score)` 索引。

### 2.3 去掉每行一个的相关子查询

**现状**：`TagMapper.xml` 的 **5 个查询**（`listAll` L49-53、`selectById` L32-36、`selectByName` L43、`listHotTags` L59、`searchByKeyword` L68）都带：

```sql
(select count(*) from post_tag pt where pt.tag_id = t.id) as use_count
```

`tag` 表每行都要跑一次 `post_tag` 的 count。**更糟的是它被 N+1 放大** —— `toPostVO` 里每个标签都调一次 `selectById`。

**方案**：
1. 改成 `left join (select tag_id, count(*) c from post_tag group by tag_id) x on x.tag_id = t.id` —— 一次聚合，外层 join。
2. 或者恢复 `tag.use_count` 的**写入**（发帖 +1 / 删帖 -1 / 换标签重算），读的时候直接读列。但历史遗留问题正是「写路径忘记减」，所以要么彻底不管这一列（推荐），要么三处写路径一起补齐。
3. 标签列表本身低频且量小，**最省事的方案是整表缓存进 Redis**（标签总数不会过万），彻底告别这条 SQL。

### 2.4 拆 `count(*)`

- `NotificationMapper.countUnread`、`PostLikeMapper.countByPostId`、`PostCollectMapper.countByPostId`、`BarMemberMapper.countByBar` 这类精确 count，在同一请求里往往只为「显示一个数字」，改为**缓存计数**或**近似值**。
- `ChatMapper.countUnread`（L54-56）完全无索引可用，必须配合 2.2 的索引 + 第三层的 Redis 未读计数。
- `PageHelper` 会为每个分页请求额外发一条 count SQL。帖子列表这种大表分页，如果前端不需要精确总页数（改成「加载更多」），可以直接关掉 count 查询，省掉一次全表扫描。

### 2.5 深分页

现状：`PageHelper.startPage`（`listPosts` L226 等）与手工 `limit #{offset}, #{limit}`（`ChatServiceImpl` L133-134）都是 offset 分页，深翻页性能线性劣化。

**方案**：聊天记录这种**天然按时间追加**的场景改**游标分页**（`where create_time < #{lastCreateTime} order by create_time desc limit 20`），配合 `(conversation_id, create_time)` 索引，任意深度都是常量成本。帖子列表可保留 offset（论坛很少翻到 100 页）。

## 第三层：Redis 缓存与计数器（把热点请求挡在 DB 之外）

**现状**：Redis 在整个项目里**只用了一个地方** —— `CommonController.checkUploadRate`（L129-136）的上传限流。点赞、收藏、关注、浏览、会话、未读、热榜全部直连 MySQL。

框架已就位（`spring.data.redis` 已配、`StringRedisTemplate` 已注入），改造是纯增量。

### 3.1 缓存热点读

| 缓存对象 | Key 设计 | TTL | 失效策略 |
| --- | --- | --- | --- |
| 热门书吧 `/hot-bars` | `cache:hot-bars` | 24h | 已有的进程内缓存**迁到 Redis**，顺带修掉多实例不一致 |
| 首页帖子列表（第一页） | `cache:post:list:{sort}:{postType}:{page}` | 30~60s | 短 TTL 自然过期，发帖时按前缀清理 |
| 帖子详情 | `cache:post:detail:{postId}` | 5~10min | 编辑/删除/审核时精确删除 |
| 标签全表 | `cache:tag:all` | 1h | 标签增删时删除 |
| 书吧列表 | `cache:bar:list` | 10min | 吧审核通过/图标变更时删除 |

**关键原则**：
- **只缓存无差别的公共数据**。「我是否点赞了」这种个性化状态**不进这个缓存**（见 3.3）。
- 缓存键要带版本或 TTL，避免「删缓存失败 → 永久脏数据」。宁可用短 TTL 兜底，也不要依赖 100% 的主动失效。
- 用 `Cache Aside`（读穿透写删除），不要用 Write Through，实现简单且足够。

### 3.2 计数器缓冲：浏览量 / 点赞数 / 评论数

**这是最适合本项目的优化**。论坛的写热点几乎全是计数器自增：

**浏览量**（最典型的可牺牲一致性场景）：
- `PostServiceImpl` L155-157：每次详情页请求都 `update post set view_count = view_count + 1`。热门帖会被反复更新**同一行** → 行锁竞争 → 大量事务排队。
- 方案：详情页只 `INCR cache:post:view:{postId}`（Redis 单线程原子，无锁竞争）；用定时任务（每 1~5 分钟）或达到阈值时，把增量**批量**刷进 DB（`update post set view_count = view_count + ? where id = ?`）。
- 展示时用 `DB 值 + Redis 增量`。丢失少量浏览量对论坛完全可接受。

**点赞 / 评论数**：
- 用户的「点赞动作」仍然必须落 `post_like`（唯一索引是幂等基准，不能只放 Redis），但 `like_count` 的**加减**可以先加在 Redis 上，再合并落库，避免每次点赞都更新 `post` 同一行。
- 或者更简单：保留 DB 自增（已经是原子写法，本身没错），只把**读路径**（列表展示的点赞数）走 Redis 缓存。先做简单的，观察行锁竞争再决定是否上缓冲。

**方案取舍建议**：先把**浏览量**做 Redis 缓冲（收益明确、风险最低），点赞数如果没观测到竞争就维持现状。

### 3.3 状态位缓存：消灭「我是否点赞了」的逐条查询

`buildCommentVO` L486-487 和帖子列表里判断「当前用户是否点赞」目前都是**逐条查 DB**。这是列表接口 N+1 的重要来源。

**方案**：用 Redis **Set** 而不是逐个 key：
- `like:post:{userId}` 存该用户点赞过的 postId 集合（SADD/SREM/SISMEMBER）
- `like:comment:{userId}` 同理
- `collect:post:{userId}`、`follow:user:{userId}`、`bar:member:{userId}`

线上路径：列表拿到 10 个 postId，一次 `SISMEMBER` 批量判断（用 pipeline 或 Lua），**10 次查询变 1 次 Redis 往返**。

**冷启动**：用户首次访问时从 DB 全量加载他的点赞集合（一个用户的点赞数有限，几 KB），之后靠写路径维护。需要设 TTL 并允许回源重建。

### 3.4 未读计数与在线态

**未读数**（`countUnread` 全表扫 + `getConversations` 每会话 count）：
- 方案：`unread:{userId}:{conversationId}` 用 `INCR` / `SET 0` 维护；群聊未读同理。
- 新消息落库时 `INCR`；用户进入会话时清零。
- 会话列表直接 `MGET` 所有未读数，**N 次 count 变 1 次 MGET**。
- 与 3.2 同样的取舍：Redis 计数可能因宕机丢失，所以提供「以 `last_read_at` + DB 重算」的回源兜底，或接受偏差（论坛未读数不准影响很小）。

**在线态**（`ChatWebSocketHandler.SESSIONS` 是**进程内 static Map**）：
- 方案：同时写 Redis `online:user:{userId}` → 实例标识，配合心跳 TTL 续期。
- 这是**多实例部署的前置条件**：不改的话用户 A 连实例 1、用户 B 连实例 2，B 发给 A 的消息会落库但**推不到**。
- 更彻底的方案是引入 Redis Pub/Sub 做跨实例消息广播（本实例无该用户连接时，publish 到频道让持有连接的实例投递）。

### 3.5 进程内缓存的问题

现在有两处 `volatile` + `synchronized` 的进程内缓存：
- `CategoryServiceImpl` L74-75 / L289-300：热门书吧 24h 缓存
- `AiBotServiceImpl` L51-52 / L334-339：AI 机器人名字索引 60s 缓存

**问题**：单实例下工作正常，但
1. `synchronized (this)` 在缓存过期瞬间会**串行化所有请求**，而重算逻辑本身含多次 DB 查询（`listAll` + 逐吧 `toBarVO` 查 owner），并发高时会形成明显毛刺。
2. 多实例部署后各实例缓存独立，主动失效（`invalidateTriggerIndex`）只在当前实例生效。

**方案**：迁到 Redis 后 `synchronized` 换分布式锁（或干脆接受短暂多算一次，用 `setIfAbsent` 抢锁、抢不到就用旧值返回）。AI 名字索引**建议保留进程内缓存**（60s TTL、数据量小、读极频繁），因为它的基准数据量小，从 Redis 读一次的成本和从 DB 读差不多，但需要接受多实例下最长 60s 的不一致 —— 对「@ 机器人触发」这个场景完全可接受。

## 第四层：MQ 与可扩展性

### 4.1 MQ 现状修正

MQ **不是没用上** —— `NotificationProducer` → `NotificationConsumer` 是真实业务链路（评论/点赞/关注/AI 回复通知都走它），有死信队列 + 3 次重试。问题在于用法：

1. **生产端在事务内发送**（见 1.3）→ 必须改为 `afterCommit` 发送。
2. **无幂等键**（见 1.4）→ 重试会重复通知。
3. **只有通知走 MQ** → 其他适合异步化的场景没接进来。

### 4.2 适合接入 MQ 的论坛场景

| 场景 | 现状 | 接入 MQ 的收益 |
| --- | --- | --- |
| **通知** | 已接入（需修幂等） | 基线 |
| **经验值累加** | 事务内同步读改写（1.1） | 发帖/评论/点赞时只发事件，消费端串行处理该用户该吧的经验，**天然消除并发丢更新**，还能做每日额度聚合 |
| **计数器落库** | 每次请求都 update | 浏览/点赞增量发消息，消费端合并批量落库（配合 3.2） |
| **计数器落库（浏览）** | 每次详情都写 | 同上，削掉最高频的写 |
| **AI 机器人回复** | 已有专属线程池 | 可迁移到 MQ 获得持久化 + 重试，但当前线程池方案已能工作，**优先级低** |
| **搜索/热榜索引重建** | 无 | 发帖/删帖事件驱动，按需重建热度分（配合 2.2） |
| **通知批量推送** | 逐条查用户 | 消费端批量聚合同一用户的多个事件，合并成一条 |

**重点推荐：经验值走 MQ**。它同时解决了 1.1 的并发丢更新（消费端按 userId 顺序处理，或用 Redis 原子累加）和事务粒度问题，是「一箭双雕」的改造。

### 4.3 削峰与限流

- **上传限流已用 Redis**（唯一的 Redis 用法），可复制到其他写接口：发帖、评论、点赞各加一层 `rate:limit:{userId}:{action}`，防止单个用户或爬虫打爆。
- **降级开关**：热门接口（列表、详情）在 DB 压力大时应能自动降级到「读缓存 / 返回旧数据」。当前没有熔断机制，可考虑引入 Sentinel 或用简单的 Redis 开关。

### 4.4 可扩展性前置条件

要让服务能横向扩容，必须先解决三项「有状态」问题，全部在上文提到：
1. **在线态** → Redis（3.4）
2. **进程内缓存** → Redis 或接受不一致（3.5）
3. **`synchronized` 单机锁** → 分布式锁（3.5）

在这三项完成前，多实例部署会导致消息推不到、缓存不一致等问题。**当前阶段可以不改，但要知道这是扩容的拦路虎。**

## 建议的实施顺序

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| **P0** | 1.1 经验原子化、1.2 唯一键兜底 + 按行数扣减、1.3 慢活移出事务、1.4 MQ 幂等 | 并发压测下计数不出错、不再有重复通知、发帖不再占用长事务 |
| **P1** | 2.1 N+1 批量改造（帖子/评论/会话/书吧）、2.2 补索引、2.3 去子查询 | 列表接口 SQL 数降到 5 次内；慢查询日志无全表扫 |
| **P2** | 3.1 热点缓存、3.2 浏览量 Redis 缓冲、3.3 状态位 Set、3.4 未读计数 | 首页/详情的 DB QPS 明显下降 |
| **P3** | 4.2 经验与计数器接入 MQ、4.4 多实例前置改造 | 可水平扩容；热点写不再直接打到 DB |

**观测先行**：动手前建议先开慢查询日志（`long_query_time=0.1`）和 Druid 的 SQL 监控，把真实的慢 SQL 排名跑出来。上面的清单是基于代码结构的推断，实测能确认优先级 —— 比如如果 `chat_message` 表还很小，2.2 的索引收益就暂时不如 2.1 的 N+1 改造。
